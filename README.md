# SentisClientOptimisation

Клиентский плагин (грузится через [Pulsar](https://github.com/SpaceGT/Pulsar/)): исправления фризов игрового клиента
Space Engineers, найденные по трейсам клиентов. Работает на любом сервере, ничего не отправляет на сервер, настроек
нет. Каждое исправление ставится само по себе: если игра изменилась и оно не подходит, оно пропускается (строка в логе
игры), остальные работают.

## Исправления

| Что | Было | Стало |
|---|---|---|
| **Воксель, который сервер забирает у клиента** (`VoxelCacheSave`) | Когда астероид или планета уходит из зоны клиента (улетел, возродился далеко), клиент сохраняет её изменённые воксели себе в кэш (`MyVoxelReplicable.OnDestroyClientInternal` → `Storage.Save`: каждый изменённый кусок записывается и сжимается), всё в игровом потоке. У сильно перекопанной карты — 3,3 с одного кадра (трейс клиента 11.11.2026). | Данные готовятся в фоновом потоке и кладутся в кэш в игровом, когда готовы. Хранилище берёт свои блокировки, игра читает его как раньше; астероид закрывается сразу (его хранилище, закреплённое, закроется, когда данные готовы). Старые данные карты убираются из кэша сразу: если сервер вернёт карту раньше, чем готовы новые, клиент не найдёт кэша и попросит карту у сервера (путь самой игры) — старые данные не берутся никогда. Новые, подоспевшие после возвращения карты, не кладутся. |
| **Удаление большого грида** (`BulkChildDelete`) | Блоки грида — его дети, удаляются по одному с последнего, и на каждый игра дважды проходила все блоки: вынимала его из списка детей поиском с начала (`RemoveByJN`) и отписывала от событий контейнера грида (каждая отписка пересобирает список подписчиков). Время растёт с квадратом числа блоков: 1,0 с из 1,6 с кадра (трейс клиента 11.11.2026). | Последний ребёнок снимается с конца списка; пока иерархия из многих детей (от 32) удаляет их, они не отписываются по одному — их подписки убираются из событий контейнера разом в конце. Вызовы заменены в самом `MyEntity.Delete` (мелкие методы игры могут быть в него встроены). На стенде, грид из 3000 ламп: 1062–1158 мс → 617–670 мс (оставшееся — системы грида и закрытие блоков, это игра). |
| **Конвейеры большого грида при его закрытии** (`ConveyorCloseUnsubscribe`) | Каждый конвейерный блок грида подписан на `IsPoweredChanged` питания конвейерной системы грида; при закрытии грида каждый отписывается сам, и каждая отписка пересобирает список всех: 0,3 с удаления грида (трейс клиента 11.11.2026, 21:55). | Пока грид закрывается (`BeforeGridClose` … `AfterGridClose`), блоки не отписываются по одному: их обработчики убираются из события разом в конце (или в следующем кадре, если закрытие оборвалось). |
| **Сетевые пулы буферов** (`PoolCap`) | `MyConcurrentBucketPool.Return` перед возвратом буфера спрашивает `Count` у стека пула, а `ConcurrentStack.Count` проходит весь стек. У пулов принятых пакетов (`MyReceiveQueue.m_messagePool`) и буферов репликации (`BitStream.BufferPool`) предела нет, после всплеска пакетов в них тысячи буферов, и каждый возврат проходит их все: 2,95 с игрового потока за минуту, до 0,45 с в кадре (трейс клиента 11.11.2026, 21:55). | У этих двух пулов предел — 512 буферов одного размера: подсчёт проходит не больше 512, лишний буфер освобождается (как игра освобождает лишнее у любого пула с пределом), во всплеске пул делает новые. Сам метод не патчится: он у обобщённого класса, Harmony из Pulsar такие не патчит (проверено тестом). |
| **Разбор пришедшего большого грида** (`GridLoadAsync`) | Когда сервер присылает грид (подлёт к базе), клиент разбирает всё его описание (`MyCubeGridReplicable.OnLoad` → `MySerializer.CreateAndRead`) в игровом потоке, потом строит грид в потоке создания сущностей: 3,6 с за минуту, 2,3 с одного кадра (трейс 11.11.2026, 21:55). | Для данных от 32 КБ остаток потока копируется (копия памяти) и разбирается в фоновом потоке; в игровом грид создаётся дальше, как игра создаёт. Репликация и так ждёт грид (в игре он тоже делается асинхронно) — ждёт на кадр-два дольше. Если разбор в фоне не удался, он повторяется в игровом потоке, как в игре. Сообщение о разделённом гриде и малые гриды — как в игре. |
| **Чертёж проектора** (`ProjectionPreclone`) | При первом обновлении проектор работает на копии чертежа (`MyProjectorBase.UpdateOnceBeforeFrame` → `Clone`: весь чертёж записывается и читается заново) в игровом потоке: 1,4 с за минуту, 1,2 с одного кадра (трейс 11.11.2026, 21:55). | Если проектор создаётся не в игровом потоке (пришедший грид строится в потоке создания сущностей), копия делается там, в `Init`; первое обновление берёт готовую. Чертёж между ними не меняется (игра хранит его как есть для сохранения), копия та же. Проектор, созданный в игровом потоке, копирует как в игре. |
| **Двигатели больших кораблей и конвейеры** (`ThrustConveyorScc`) | Компонент тяги грида держит двигатели в группах, связанных конвейерами в обе стороны. Когда приходят блоки (грид пришёл, построен, состыкован), каждый двигатель проверяет каждую группу двумя обходами графа конвейеров (`Register` → `FindConnectedGroups`), каждая изменённая точка — двумя обходами (`FindMutuallyReachableGroups`), и при слиянии групп так же; всё под одной блокировкой на все гриды мира, параллельное обновление ждёт её: 13,5 с за две минуты, 3,8 с одного кадра (трейс 11.11.2026, 22:30). | Группы точки — те, чья первая точка взаимно достижима с ней, то есть в её компоненте сильной связности, одной для всех её точек (обход выдаёт и начало). В пределах одного `UpdateConveyorSystemChanges` (граф конвейеров меняется только в игровом потоке, не во время параллельного обновления) компонента обходится один раз — вперёд и обратно, как игра в `FindMutuallyReachableGroups`, — и хранится для всех её точек; группы выбираются из неё, как выбирает игра. Тест сверяет выбор с попарными обходами на случайных графах. Вне этого — всё как в игре. |
| **Пришедший воксель с данными** (`VoxelLoadAsync`) | Изменённый астероид или планета приходит с данными; клиент читает их и строит хранилище (`MyVoxelReplicable.OnLoad` → `MyStorageBase.Load`) в игровом потоке: 1,8 с одного кадра (трейс 11.11.2026, 22:30). | Остаток потока копируется и читается в фоне, хранилище астероида строится там же (планеты — её генератор, кэши карт высот — в игровом потоке, как в игре); в игровом потоке карта создаётся или получает хранилище, как в игре. Если фон не справился — читается снова в игровом потоке. Карты без данных — как в игре. |
| **Хранилище планеты: принудительная сборка мусора** (`PlanetDetailNoGc`) | Каждый раз, когда строится хранилище планеты (планета пришла с данными), её генератор читает текстуру деталей (`MyPlanetTextureMapProvider.GetDetailMap`) и сразу принудительно запускает полную блокирующую сборку мусора: 1,6 с одного кадра, сама текстура — 0,05 с (трейс 11.11.2026, 22:56). | Сборка там не вызывается: она только раньше освобождала буферы чтения, среда освободит их, когда понадобится. Сборки при первом чтении карт типа планеты (раз на тип) — как в игре. |
| **Энергия при стыковке и расстыковке** (`GroupPowerOnce`) | Грид, входящий в логическую группу или выходящий из неё (`MyCubeGridSystems.OnAddedToGroup` / `OnRemovedFromGroup`), сразу пересчитывает распределение энергии всей группы; при слиянии или разделении групп так делает каждый перенесённый грид, а в следующем кадре игра всё равно пересчитывает всё заново: 1,5 с за трейс (11.11.2026, 22:56). | Пока создаётся или рвётся связь (`MyCubeGridGroups.CreateLink` / `BreakLink`), пересчёты гридов откладываются и делаются по одному на распределитель в конце — последний пересчёт игры над теми же блоками даёт то же распределение. Грид, пришедший или ушедший сам по себе, — как в игре. |
| **Конвейерные линии и энергия** (`LinePowerOnce`) | Когда меняются конвейеры или энергия грида, каждая конвейерная линия спрашивает распределитель, есть ли электричество (`MyConveyorLine.UpdateIsWorking` → `ResourceStateByType`); изменившаяся линия помечает конвейеры на пересчёт, и вопрос следующей линии пересчитывает всё распределение — пересчёт на линию: 4,7 с за трейс, 2,1 с одного кадра (трейс 11.11.2026, 23:29). | В игровом потоке линии одного распределителя за кадр берут состояние, полученное первой. Распределитель остаётся помеченным на пересчёт — его сделает следующий вопрос игры; если от этого изменится электричество, событие питания конвейерной системы снова оповестит линии, как в игре. |
| **Звук грида и апгрейд-модули** (`PowerReadOnce`) | Звук грида каждый кадр, а каждый апгрейд-модуль по три раза за тик в 100 мс смотрят состояние его энергии (геттер `MyResourceDistributorComponent.ResourceState` — тот же `ResourceStateByType` с пересчётом); когда распределитель грязный, каждый взгляд пересчитывает всё распределение: 1,6 с и 1,9 с за трейс (трейс 12.11.2026, 12:27), в том числе в кадрах по 1,3 с. | В игровом потоке эти взгляды берут тот же ответ об энергии, что уже получен в этом кадре первым вопросом (тот же кэш, что у линий конвейеров — вопрос у них тот же): первый пересчитывает, остальные берут готовое. Свои вопросы игра пересчитывает как пересчитывала; новое состояние звук и лампочки модулей могут увидеть на кадр позже, чем в игре, — между взглядами они симуляцию не двигают. |

Юнит-тесты — `SentisClientOptimisation.Tests` (`dotnet test SentisClientOptimisation.Tests`): каждое исправление ставится на сборки клиента игры, пул с пределом и без, снятие подписок, снятие ребёнка с конца, копия потока с любого бита, выбор групп двигателей как у попарных обходов на случайных графах, копия чертежа берётся один раз, ответ об энергии
держится только своим кадром и вне игрового потока спрашивается как в игре. Проверка на стенде — `reg_client_bulk_delete` (SentisTests): исправление удаления грида загружается из собранной dll в
сервер (код `MyEntity.Delete` тот же), только на время проверки. Сохранение вокселя бывает только на клиенте.

## Установка

Закройте игру и запустите `SentisClientOptimisation-<версия>-Setup.exe`.
Установщик обнаруживает Legacy и Interim в `%APPDATA%\Pulsar` и предлагает выбрать режим.
Legacy запускает SE1 на .NET Framework 4.8, Interim — на .NET 10 через слой совместимости;
Modern относится к SE2. Если выбранный вариант отсутствует, установщик предлагает скачать Pulsar
с официального GitHub. Для Interim при необходимости устанавливается .NET 10 Desktop Runtime
в `%LOCALAPPDATA%\SentisClientOptimisation\dotnet` без прав администратора.
Предварительный запуск игры не требуется.
Установщик кладёт DLL в каталог Local выбранного режима (у Interim возможен штатный fallback на Legacy),
включает плагин в текущем профиле,
настраивает серверный GC и создаёт ярлык «Space Engineers (Pulsar)» с иконкой Sentis.
Запускайте игру этим ярлыком. Права администратора не нужны.

Удаление — через «Установленные приложения» Windows: убирает плагин, запись профиля, ярлык и настройки GC
(при изменённом конфиге сохраняет посторонние настройки). Сам Pulsar и остальные плагины остаются.
В логе игры при старте: `SentisClientOptimisation: VoxelCacheSave on` и `SentisClientOptimisation: GC: server, ...`.
Обновление Pulsar может перезаписать его конфиг; в этом случае повторите установку.

Сборка ссылается на клиент игры (`SeBin`, по умолчанию `C:\Program Files (x86)\Steam\steamapps\common\SpaceEngineers\Bin64`)
и на Harmony из Pulsar (`PulsarLib`, по умолчанию `%APPDATA%\Pulsar\Libraries\Legacy`; где Pulsar нет — на тот же
`Lib.Harmony` из NuGet, в рантайме плагин связывается с Harmony, который Pulsar уже загрузил).

`powershell -NoProfile -ExecutionPolicy Bypass -File tools/release.ps1 -Version 0.2.1`
собирает `dist\SentisClientOptimisation-0.2.1-Setup.exe`. Нужны .NET SDK и Inno Setup 6.5+;
путь к компилятору можно передать через `-Iscc` или `INNO_COMPILER`.
Тег `0.2.1` (или `v0.2.1`) запускает workflow сборки и публикации EXE;
«Run workflow» собирает EXE без релиза. Библиотеки игры workflow получает через SteamCMD и не включает в установщик.

Проверки упаковки: `python tools\test-packaging.py`;
проверки установки и удаления в изолированном профиле:
`powershell -NoProfile -ExecutionPolicy Bypass -File tools\test-install.ps1`.
`tools\test-pulsar-install.ps1` проверяет отдельную установку Pulsar.
Для тихой установки с явным согласием на скачивание Pulsar:
`/VERYSILENT /RUNTIME=Legacy /INSTALLPULSAR=1` (или `/RUNTIME=Interim`);
без `INSTALLPULSAR=1` тихая установка не скачивает отсутствующий Pulsar.
Полная проверка EXE — `tools/test-exe.py --archive <официальный win-x64.zip> --runtime Legacy --download --gui-consent`;
повторить с `--runtime Interim`. Тест использует изолированные APPDATA, LOCALAPPDATA и Desktop,
проверяет реальные кнопки согласия, профиль, GC, иконку и удаление; игру не запускает.

## Сборка мусора клиента (отдельно от плагина)

В трейсе клиента (11.11.2026, 22:56) игровой поток четверть времени (15 с из 59) стоял на сборке мусора: сборщик
однопоточный (workstation), куча 2–3 ГБ, больше всего — проход по карточкам старшего поколения. `tools\gc\enable-gc.ps1`
включает для `Legacy.exe` (игра через Pulsar) то, что на тестовом сервере дало короткие частые сборки вместо длинных:
серверный GC на 4 кучи (`gcServer`, `gcConcurrent`, `GCHeapCount=4`, `GCNoAffinitize` в `%APPDATA%\Pulsar\Legacy.exe.config`,
копия — `Legacy.exe.config.bak-before-gc`) и ярлык на рабочем столе «Space Engineers (Pulsar, GC).cmd» с бюджетом gen0
32 МБ (`COMPlus_GCgen0MaxBudget=2000000`, только для этого запуска). Вернуть — `tools\gc\disable-gc.ps1`. Плагин пишет
режим GC в лог игры: `SentisClientOptimisation: GC: server, ..., gen0 budget 2000000`. Обновление Pulsar может
перезаписать конфиг — тогда в логе будет `workstation`.
